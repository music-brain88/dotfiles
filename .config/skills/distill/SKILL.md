# /distill — 軽量蒸留(蒸留パイプライン層2)

`/session-log` が層1(セッション → ResearchNotes)の捕獲を担うのに対し、本スキルは層2
(ResearchNotes / LiteratureNotes → PermanentNotes)の蒸留を担う。
軽量蒸留(本スキル)とフル `/learn` 理解ゲートの2段階のうち、標準ルートがこちら。
背景となる設計は vault の `ProjectNotes/Obsidian蒸留パイプライン設計書.md`(§2 設計原則・§5 蒸留セッション SOP)。
**運用ルール・パスの単一の真実は `Zettelkasten/MOC-ObsidianWorkflow.md`**(下記「前提情報」参照)であり、
本スキルの記載と食い違う場合はそちらを優先する(session-log と同じ構造)。

## 起動方法

- **明示起動**: `/distill` または `/distill <ノートのパスや名前>`
  - 引数なし: 蒸留キューから候補を提示する(下記手順1)
  - 引数あり: 指定ノートをそのまま対象にし、候補選定はスキップして手順2から始める
    (`/wtclean` の収穫ステップなど、対象が既に決まっている呼び出し元を想定)

## 実行環境トリアージ

本スキルは手順の宣言であり、特定の実行環境に依存しない。書き込み手段は以下の優先順で選ぶ:

| 環境 | 書き込み手段 |
|---|---|
| ローカル CLI エージェント(Claude Code・Copilot CLI 等) | ファイル直接読み書き |
| Claude Desktop / claude.ai(クラウディア) | Filesystem MCP(許可ディレクトリに vault が必要) |
| 書き込み手段なし(モバイル・MCP未接続) | 転記内容をノート全文として chat に markdown で出力し、ユーザーが後で取り込む |

いずれの場合も手順・フォーマット・記録の原則は同一。

## 実行環境フォールバック

- AskUserQuestion が使えない環境(Copilot CLI 等)では、番号付き選択肢のテキスト提示で代替する

## 前提情報

- Vault: `/home/archie/Documents/Obsidian/Zettelkasten/`(WSL でのパス解決は `nix/modules/wsl.nix` の symlink に依存。書き込み手段は上記「実行環境トリアージ」に従う)
- **パス・運用ルールの単一の真実**: `Zettelkasten/MOC-ObsidianWorkflow.md` の「蒸留状態の宣言」と「エージェント向けの宣言」。本スキルの記載と食い違う場合はそちらを優先し、差分を報告する
- 蒸留キューの定義(MOC 側が正): `distilled_to` が空 **かつ** `triage: candidate` のノート。対象は ResearchNotes・LiteratureNotes(Clip) 共通
- キューの検索方法: Obsidian の Base ビュー(`ResearchNotes.base` 等)は GUI 専用のため、エージェントは `ResearchNotes/` `LiteratureNotes/` 配下の frontmatter を Grep で横断検索してキューを求める
- PermanentNote の置き場は MOC「エージェント向けの宣言」を参照。候補が複数ある場合はユーザーに確認してから書き込む

## 手順(軽量蒸留 SOP、1件目安10〜15分)

### 1. 候補提示

引数がない場合、蒸留キューから2〜3件を AskUserQuestion で提示し、ユーザーに1件選んでもらう。
候補が少ない・ゼロの場合は素直にその旨を報告する(無理に埋めない)。

### 2. 問いかけ

対象ノートを読み、因果の再構成を促す問いを2〜3投げる。一度に全部聞かず、応答を見ながら段階的に進める:

- なぜこれが重要か
- 何と繋がるか(既存の PermanentNote・プロジェクトとの関係)
- 一言で言うと何か

### 3. 人間が語る

ユーザーが自分の言葉で核心を話す・書く。**ここは人間にしかできない工程** —
エージェントは代筆・要約・言い換えをしない。

### 4. 逐語転記

ユーザーの発話を **逐語ベースで** PermanentNote に転記する。整形(改行・見出し・箇条書き化)のみ許可し、
加筆・要約・エージェントの言葉の混入は禁止。書き込み前に転記内容をユーザーに提示し、最終確認を取る。

> 逐語転記は運用原則に適合する: 出所が人間の発話であれば「LLM生成物」ではないため、
> PermanentNote を人間の言葉のみに保つ制約と矛盾しない。

### 5. 配管

- 元ノートの `distilled_to` に、新規(または追記した)PermanentNote への `[[リンク]]` を埋める
- PermanentNote 側にも関連ノートへ `[[リンク]]` を張る(実際に関連があるものだけ — 誠実なエッジの原則。無いエッジを捏造しない)
- 必要なら MOC への追記を**提案**する(強制しない)

## /learn への昇格ハンドオフ

手順2〜3の途中で「理解が浅い」「もっと深掘る価値がある」と判明したら、`/learn` 理解ゲートへの
昇格を**提案**する(soft — 強制しない)。昇格した場合、本スキルの手順4〜5(転記・配管)は行わず
`/learn` 側の Persistence に委ねる。

## 他スキルとの役割分担

- `/session-log`: 層1(セッション → ResearchNotes)の捕獲。本スキルはその先の層2を担う
- `/learn`: 理解の検証(教師モード)。深掘り時に本スキルからハンドオフを受ける。直交性を保つため、
  本スキル自体は理解ゲートを兼任しない
- `/wtclean`: 作業サイクル完了直後の「収穫ステップ」から、対象ノート指定で本スキルを呼ぶ想定
  (別 Issue での実装予定。本スキルは呼ばれる側として引数指定に対応するのみ)

## 完了報告

転記した PermanentNote のパス、更新した元ノートのパス(`distilled_to`)、追記した関連リンクや MOC
があれば報告する。`/learn` へ昇格した場合はその旨を明記する。vault は git 管理下だが、書き込み自体は
通常編集でよく、コミットはユーザーの日次運用に委ねる(session-log と同様)。
